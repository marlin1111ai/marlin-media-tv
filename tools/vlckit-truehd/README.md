# VLCKit with TrueHD — the recipe

VLCKit 4.0.0-a24 for tvOS, rebuilt from VideoLAN's own scripts with one change: `0007-truehd-enable.diff` removes the hunk of VLCKit's patch 0007 that switches off ffmpeg's MLP/TrueHD decoder, so Wonder Woman's TrueHD 7.1 track decodes to 7.1 PCM (DECISIONS.md D012).
Rerun: `tools/vlckit-truehd/build.sh` (builds in `~/vlckit-build` — override with `BUILD_DIR=`, no spaces allowed, VideoLAN's scripts break on them; network: libvlc clone, host-tool and contrib tarballs; hours, not minutes). It writes `~/vlckit-build/build.log` and copies the result to `Frameworks/VLCKit.xcframework`, which the Xcode project links by path (D013). `Frameworks/` is not in git.
`m4-1.4.21.tar.gz` and `gettext-0.26.tar.gz` are pre-fetched from ftp.gnu.org into libvlc's `extras/tools/` (checked against its SHA512SUMS) because the GNU mirrors and VideoLAN's contrib mirror do not reliably carry them.
The build needs python.org Python 3.10+ installed at `/Library/Frameworks/Python.framework` (the default of the python.org installer): VideoLAN's script puts only that framework, its own tools and `/usr/bin` on the build PATH, and the meson it builds refuses Xcode's Python 3.9.6.
GNU make 4.4.1 is built into `~/vlckit-build/tools` and passed as `VLC_PATH` (VideoLAN's hook for extra host tools): Xcode's make 3.81 breaks the jobserver with the ninja VLC's tools build, and the build stops in the contribs.
`0018-avcodec-audio-coalesce-TrueHD-MLP-frames.patch` (pass 1d, D015) is a libvlc patch in VLCKit's own patch format: `build.sh` copies it into `libvlc/patches/` so VideoLAN's script applies it after the seventeen upstream ones. It makes the avcodec audio decoder gather the 40-sample TrueHD/MLP frames into ~20 ms blocks before the audio output; no other codec is touched.
`0019-videotoolbox-dpb-no-latency-bump-ahead-of-arriving-picture.diff` (pass 1e, D017) is a libvlc patch in `git format-patch` form, stored as `.diff`; `build.sh` copies it into `libvlc/patches/` as `0019-….patch` so it is applied after 0018. In VideoToolbox's picture reorder buffer (`modules/codec/videotoolbox/dpb.c`), a release triggered only by the max-latency count no longer outputs pictures that follow the arriving picture in display order; VLC's own `dpb_test.c` "Max latency requirements" expectation, which encoded the out-of-order release, now expects display order. It affects HEVC and H.264 (the same reorder code), nothing else.
`build.sh` sets `TVOS_DEPLOYMENT_TARGET = 26.0` in VLCKit's own `VLCKit.xcodeproj` before building (pass 1e rerun 3, D018): Xcode 27 rejects tvOS deployment targets below 15.0 and the project ships 11.0, which VideoLAN's archive call does not override; libvlc's own minimum is unchanged.
