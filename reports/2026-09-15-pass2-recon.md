### 2.5 Traced from the server's own docs — not observed, not sent

Source: the marlin-media repo (`marlin1111ai/marlin-media`), read this pass —
`reports/2026-09-13-pass4a-playback-state.md` §"For the client foreman",
`reports/2026-09-13-pass4b-date-added.md` §"For the client foreman", and `COLD-START.md:47`,
`:50`–`:51` there. **Nothing was PUT.**

**`PUT /api/files/{fileId}/playback` — request shape (docs):**

```
PUT /api/files/{fileId}/playback
Content-Type: application/json

{"position": 1830.5, "watched": false}      # either key may be omitted
{"position": 1830.5}                        # position only, watched unchanged
{"watched": true}                           # mark finished, position unchanged
```

Response `200` is the playback block:

```json
{ "position": 1830.5, "watched": false, "last_played": "2026-09-14T00:43:18Z" }
```

`404 {"error":"file not found"}` for an unknown id; `400` for bad JSON, unknown keys or a negative
position. `last_played` is set to the server's current time **on every write**, RFC3339 UTC or null.

Corroborated by the handler's own field tags (`server/playback.go`, same repo): request
`Position *float64 \`json:"position"\``, `Watched *bool \`json:"watched"\``; both optional, applied
with `COALESCE`, so an omitted key leaves the column unchanged.

**Independently observed here:** there is no read-back route — `GET /api/files/1/playback` returns
`404 page not found` (text/plain). The playback block is read only off the item or off
continue-watching.

**`GET /api/continue-watching?limit=N` — entry shape (docs):** `limit` defaults to 50, max 200.
Items with `position > 0` **and** `watched == false`, newest `last_played` first, one entry per
file. Shared fields: `kind` (`movie` | `episode` | `video`), `file_id`, `stream`, `playback`,
`duration`. A movie entry adds `movie_id`, `title`, `year`, `edition` (null when the file has no
edition tag), `artwork`; an episode entry adds `show_id`, `show_title`, `season`, `episode`,
`title`, `artwork` (show poster/backdrop **plus `still`**); a video entry adds `video_id`, `title`.
Artwork URLs are server-relative. The docs' example episode entry:

```json
{
  "kind": "episode",
  "file_id": 8,
  "stream": "/stream/8",
  "playback": { "position": 1425, "watched": false, "last_played": "2026-09-14T00:43:18Z" },
  "duration": 3128.5614,
  "show_id": 2,
  "show_title": "The Magicians",
  "season": 1,
  "episode": 1,
  "title": "Unauthorized Magic",
  "artwork": { "poster": "…", "backdrop": "…", "still": "…", … }
}
```

**`added` on a video item (docs):** `added` is on every movie, show **and video** item, in both
list and detail responses, RFC3339 UTC; sort descending for Recently Added. It is the first time
the server saw the movie folder, show folder or video file, and a new edition or episode inside an
existing folder does not move it (server D034).

**Server-side rules worth carrying into the build (docs, server DECISIONS.md):** D033 —
continue-watching *is* `position > 0 and watched = false`, newest `last_played` first, so an item
leaves the row the moment the client marks it watched. D032 — playback state is keyed by file
**path**, exposed by file id, so it survives a rescan and a file that vanishes and returns. The
server's own pass-4a report records as an open question that **the server never sets `watched`
itself; only the client does.**

for `httpMethod`, `"PUT"`, `"POST"` and `URLRequest` across `Marlin Media TV/*.swift` returns

`continue watching`/`continue-watching`, `recently added`, `/api/continue-watching` or

## 6. SWEEP and STANDALONE

No item is added here; this only sorts the work the four features imply.

### SWEEP — independent, additive, clear of the do-not-touch list

1. **Recently Added sort.** One enum case and three sort branches on a field already decoded; the
   menu picks it up from `allCases` by itself. Touches no network write and no player file.
2. **A `continueWatching()` GET on `APIClient` plus its Decodable entry type.** Purely additive to
   `ServerAPI.swift`/`Models.swift`; no existing call path changes.
3. **The Continue-watching row on frames 01 and 02.** A new view above the existing grid in
   `LibraryScreen`, fed by item 2; the grid, the header and the sort control are untouched.
4. **The detail screens' resume/watched readouts** — frame 06's watched pill, "Resume · N min
   left" with its bar, "Start over" and "Mark unwatched"; frame 08's per-episode state column,
   in-still progress bar and unwatched count; frame 09's Resume/Start over. These read `playback`,
   which is already decoded and already on screen's data; view-layer work in three files that the
   player never enters.
5. **A `putPlayback(fileId:position:watched:)` method on `APIClient`.** The method itself is one
   additive function in `ServerAPI.swift` — it is *calling* it from the player that is standalone.

### STANDALONE — the player/VLCKit path, fragile paths, or plainly hard

1. **Writing the position every 10 s and on pause, stop and exit.** All four sites are inside
   `PlayerModel.swift`, the same file as the D021 scrub and D008 frame step, and one of them is
   `dismiss()`, which also tears VLCKit down in a fixed order.
2. **Marking watched at 90 %.** Same player timing path as item 1, and it has to survive the
   player's exit ordering to be written at all.
3. **Starting a title at its saved position.** A seek on the VLCKit path at start-up — exactly the
   ground where passes 1f–2g found the paused-seek read-ahead, the clock-anchor laps and D014's
   cue handling; it also has to sit alongside D016's parse-before-play.
4. **Anything requiring a change to `PlayerHost.swift`.** That file carries the uncommitted pass-2g
   harness hook and is on the do-not-touch list; any work that would edit it stops first.

## 7. Open questions

Behaviours a build would need that neither the frames of §3 nor the owner's calls of §4 state.
Questions only.

1. When a partly watched title is opened and Play is pressed, does it resume at the stored position
   or start at zero?
2. Frame 06 draws only the "Resume · N min left" button and no "Play" variant — what does that
   button read, and how does it behave, when the movie has no stored position?
3. Is there a lower bound below which a stored position is ignored and the title treated as
   unstarted, and an upper bound near the end above which it is treated as finished rather than
   resumable?
4. Can watched be cleared, and by what control — is frame 06's "Mark unwatched" the only route, and
   does it also clear the stored position or only the flag?
5. Does the button's wording flip to "Mark watched" when a title is unwatched, as the prototype
   does, and is that a state the frames intend?
6. When a title is marked watched at 90 %, does playback of the remaining 10 % continue to write
   positions, and does reaching the end write anything further?
7. Does "Start over" write position 0 before playing, or only play from 0 and leave the stored
   position until the next periodic write?
8. What does the app do when a playback write fails or the server is unreachable mid-film — retry,
   drop it silently, or show the failure as the library screen shows its errors?
9. Does the 10 s position write continue while the film is paused, or only while it is playing?
10. After a scrub landing or a skip, is a position written immediately, or only at the next 10 s
    tick?
11. Which file's position does a multi-edition movie show on the detail screen and in the
    Continue-watching row, given that `playback` is per edition and the frames draw one button?
12. For a show, which episode does a Continue-watching card stand for once an episode is finished —
    the one with a position, or the next unwatched one?
13. Does finishing an episode do anything to the next one, and does the show's "N unwatched" count
    in frame 08 count a partly watched episode as watched or unwatched?
14. What does frame 08's per-episode column show for an episode with a position but no watched
    flag, versus one that is watched, versus one never started — and does "Watched ✓" ever carry a
    count as frame 06's "Watched 2 ×" does?
15. Does the app track a watch **count** at all, given that frame 06 draws "Watched 2 ×" and the
    server's `playback` block carries only a boolean?
